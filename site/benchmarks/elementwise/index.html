Benchmarks

Elementwise

Vector add bandwidth on large arrays against MLX, plus the time Enceladus takes to compile a kernel from Python to MSL.

What it measures

bench_elementwise runs the vector add from examples/01_vector_add.py, out = x + y, on 226 elements in float32 and float16, and on 228 elements in int8. That's 256 MB per array in float32 and int8, and 128 MB in float16, far larger than the GPU's caches. The script measures the following:

  • Enceladus with BLOCK=1024 and BLOCK=4096, in float32, float16, and int8, as the minimum of 20 GPU-timed runs.
  • MLX's x + y on the same shape and dtype, as the minimum of 20 wall-clock runs after 10 warmup runs. The script measures MLX again for each row.
  • The compile time of the vector add, from the Python frontend to MSL, as the median of 50 compilations. This excludes Metal's own compilation of the MSL.

GB/s counts three arrays of traffic: two reads and one write.

Reading the results

  • All three dtypes reach the same bandwidth. Every configuration runs at 231.5-238.1 GB/s. float16 moves half the bytes in about half the time, and int8 adds four times as many elements as float32 in the same time, so the kernel is bound by memory bandwidth, not by instruction count.
  • Block size matters little. BLOCK=1024 is slightly faster than BLOCK=4096 in every dtype: 236.6 against 233.4 GB/s in float32, 238.1 against 237.2 GB/s in float16, and 236.4 against 231.5 GB/s in int8.
  • Enceladus leads MLX by 2-12%. In float32, the 2-4% lead is about the size of MLX's wall-clock overhead. In float16 and int8, Enceladus leads by 8-12%, and MLX takes 0.17-0.35 ms longer, more than the overhead of about 0.1 ms explains.
  • Compilation is cheap. At 0.46 ms, the Python-to-MSL step costs less than one launch of this kernel on 256 MB arrays.

For guidance on block sizes and SIMD groups for memory-bound kernels, see Performance.
